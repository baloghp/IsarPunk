# IsarPunk Workshop — Playtest Protocol

**Purpose:** Rehearse the workshop with Circular Munich friends and family before production printing. This is a safe setting to test the flow and collect an adult/teacher perspective. It is not evidence of how 12–15-year-olds will respond.

## What this playtest should answer

- Can people follow the activities and card instructions without repeated facilitator rescue?
- Do both laptop stations work offline, and do their tasks fit the time available?
- Is the Mission 1 path mechanic clear before teams use it in Mission 2?
- Is Mission 2's card volume manageable, and do safety steps and shop referrals make sense?
- Which materials, instructions, transitions, or timings need changing before the next test or print?
- From a teacher's perspective, could this be hosted in a real class: age fit, room setup, preparation, safeguarding, and evidence of learning?

## Rough test kit

Use working drafts; do not laminate or order final quantities yet.

- [ ] Two pre-2018 laptops: one for USB boot / distro tasting, one with the offline Linux install and apps
- [ ] Mint and Bazzite live USBs, plus at least one known-good spare
- [ ] Test both machines without network; confirm power, boot keys, displays, audio, and the apps needed for F1/F2
- [ ] Draft Set A layer-sort cards; Measure In/Out sheets using the integrated guide's B1–B6 and E1–E3 rows
- [ ] Draft S1, O, C, S2, H, and D card sets, grouped for the intended reveal sequence
- [ ] F1/F2 station sheets, five A2 boards, markers, and arrows
- [ ] Distinct colour dots for each tester, with no names or colour-to-person key
- [ ] Current partner/shop crib and a draft take-home sheet; clearly mark any simulated or unconfirmed listing
- [ ] Intro slide and a visible timer; printed observer sheet or notebook
- [ ] Photo consent if taking photos; otherwise record counts and notes without identifiable images

Assign one person to facilitate, one to observe and time, and one to manage the stations if enough people are available. Rotate only if testing facilitator hand-offs is itself a goal.

## Measures

### 1. Before and after: same response rows

Use the integrated guide's exact B1–B6 opinion and E1–E3 confidence wording both before and after the session. Each tester marks `STIMMT`, `UNSICHER`, or `STIMMT NICHT` privately, then places their colour together with the group. Do not interpret a small adult sample as a youth impact result.

For the playtest, the main value is whether the rows are understandable and whether participants can answer confidently. Record any wording questions. Compare aggregate movement only as a signal that the workshop may be landing; do not identify individual colours in notes or photos.

### 2. Observer log: record what happens

For each beat, record:

| Beat | Start/end time | Completed? | Help needed | Confusion or failure observed |
|------|---------------|------------|-------------|-------------------------------|
| Primer / layer sort | | | | |
| Measure In | | | | |
| Station A | | | | |
| Station B | | | | |
| Win10 + Oma | | | | |
| Mission 1 | | | | |
| Mission 2 | | | | |
| Measure Out / wrap | | | | |

Use a simple help code: `0` = self-started, `1` = one hint, `2` = repeated explanation or facilitator intervention. Note the exact card, instruction, machine, or transition involved.

Also capture these checks:

- [ ] USB boot reaches a usable desktop; no installation begins
- [ ] F1 tasks are completed, including finding Terminal and running `fastfetch`
- [ ] F2 tasks are completed using the offline apps
- [ ] Both station groups get hands-on time and the planned swap works
- [ ] Mission 1 produces a coherent path and one action pledge per person
- [ ] Mission 2 produces a plausible route with safety considered before destructive or install actions
- [ ] Repair-shop referrals are named only when a repair route calls for one
- [ ] Every tester can identify their pledged action at wrap

### 3. Participant debrief

Ask these after Measure Out. Capture short answers, including dissent; do not turn the discussion into a vote on whether the workshop was “good.”

1. What is one thing you understand now that was unclear before?
2. At what point did you feel most unsure what to do next? What would have helped?
3. Which card or instruction did you have to reread, interpret, or ask about?
4. Did the laptop activities make Linux feel more approachable, less approachable, or unchanged? What specifically caused that?
5. Did any safety instruction feel missing, late, or hard to follow?
6. Did the shop hand-off feel like a useful and credible next step? What information would you need to act on it?
7. Which action you pledged feels realistically doable, and what might stop you?
8. What should be removed, shortened, or made clearer before this is tried with a class?

### 4. Adult / teacher-perspective debrief

Ask testers to answer as adults who might host or support a school session, not as proxies for students:

1. What age range do the language, examples, and tasks seem suited to? Which parts led you to that view?
2. What would a teacher need to prepare or know before the workshop day?
3. Are the timing, room, power, device, and facilitator requirements realistic for a school?
4. Is any content likely to feel patronising, alarming, politically loaded, or technically misleading to students or families?
5. What safeguarding, consent, or school-policy concern would you raise before booking?
6. What would you want students to take away, and what visible evidence would convince you they learned it?

## Source of truth

The facilitator guide now contains the card and sheet wording, artifact quantities, and run instructions under each beat. During the playtest, record any mismatch between printed drafts and that file as a finding; do not maintain a parallel deck document.

## After the playtest

- [ ] Consolidate observer notes while the session is fresh
- [ ] Separate blockers before print from later improvements
- [ ] Record and resolve playtest findings in the facilitator guide and tracker
- [ ] Retest any major changes that affect timing, safety, or the Mission 2 mechanic
- [ ] Freeze card IDs only after the team accepts the tested version
